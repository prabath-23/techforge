## 1. Payment system (like Stripe or a checkout)

### What it must do

Accept payments by card, UPI or wallet; **never charge anyone twice**; never lose a payment; support refunds; pay merchants; and match our records against the banks' records every day.

### The design

### The hard parts

- **Idempotency everywhere.** The client sends an idempotency key; the server stores key → result with a uniqueness guarantee; the same key is passed on to the processor. This is the single most important property of any payment system.
- **"Unknown" is a real state.** A timeout doesn't mean failure — the money may have moved. Mark the payment as pending, then confirm via the processor's status API or webhook.
- **Double-entry ledger.** Every movement is recorded as entries that add up to zero (money leaves one account and enters another). Entries are never edited; mistakes are corrected with new entries. Amounts are stored as whole numbers of paise/cents, never floating-point numbers.
- **Strong consistency** for money: a relational database with transactions (or Spanner-like databases at global scale).
- **Reconciliation:** banks and processors make mistakes too. Comparing records daily catches them.
- **Security:** raw card numbers are handled only by certified systems (PCI DSS); everything else uses tokens.

### The hard parts

- **Priority isolation (bulkheads):** OTPs and security alerts get separate queues and workers. A 50-million-message marketing blast must never delay someone's login code.
- **Deduplication:** producers pass an event ID; the same event never notifies a user twice (idempotency).

- **Vendor reality:** each provider has rate limits and outages; keep a backup provider for critical channels and remove expired device tokens.

## 3. Collaborative document editing (like Google Docs)

### What it must do

Many people edit the same document at the same time and see each other's changes within a fraction of a second; everyone ends up with **exactly the same** document; cursors are visible; offline edits merge when you reconnect; full version history.

### The design

### The hard part: concurrent edits

Two people edit at the same moment; their edits were based on slightly different versions of the document. Two families of solutions:

- **Operational Transformation (OT)** — Google Docs' approach: a central server orders all operations and **transforms** each one against the operations that happened concurrently ("you inserted at 52, but someone deleted 5 characters before that, so your insert now goes at 47").
- **CRDTs** (conflict-free replicated data types): give every character a unique, ordered identity so that edits **commute** — they can be applied in any order and still produce the same result, even without a central server. Ideal for offline-first and peer-to-peer apps (libraries like Yjs and Automerge); Figma uses related ideas.

Either way: route all editors of a document to one server, keep an append-only operation log, take periodic snapshots, and check permissions on every operation.

## 4. File storage and sync (like Dropbox or Google Drive)

### What it must do

Store files of any size; keep them in sync across your laptop, phone and the web; upload only what changed; let you share files; keep old versions; never lose data — at the scale of exabytes.

### The design

### The hard parts

- **Blocks addressed by their content.** Files are split into blocks (around 4 MB), and each block is named by its **hash**. Identical blocks — across versions, or even across different users' identical files — are stored **once** (deduplication). A small edit uploads only the changed blocks.
- **Smarter splitting:** inserting one byte at the start of a file would shift every fixed-size block. **Content-defined chunking** with a rolling hash (Algorithms track, chapter 7) places block boundaries based on the content itself, so an insert only changes nearby blocks.
- **Metadata must be strongly consistent;** block storage can simply be durable and huge. Dropbox famously moved hundreds of petabytes from AWS S3 into its own storage system, Magic Pocket, to cut costs.
- **Conflicts:** if two devices edited the same version offline, keep **both** ("report (Ben's conflicted copy).docx") rather than silently losing one.
