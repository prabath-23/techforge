## Why these matter

The big protocols (IP, TCP, DNS, TLS, HTTP) get most of the attention, but day-to-day engineering constantly touches a long tail of others: you SSH into servers, mount network drives, sit behind corporate proxies, debug clock drift that breaks TLS and authentication, and occasionally meet industrial equipment speaking protocols designed in the 1970s. This module gives each one a clear mental model.

## SSH: a secure remote shell

SSH (port 22) opens an encrypted channel to a remote machine. The client first verifies the **server's host key** (that "fingerprint" prompt the first time you connect protects you from impostors), then authenticates the **user**, ideally with a key pair rather than a password. Inside one connection, SSH can carry an interactive shell, file copies (scp/sftp), and **port forwarding** tunnels.

> [!WARN] If SSH warns that a host key **changed**, don't just delete the old entry — the server may have been rebuilt, or someone may be intercepting the connection. Check with whoever runs the server.

## FTP and SMB: moving and sharing files

**FTP** (1971) uses two connections — a control channel for commands and a separate data channel for each file — and sends everything, including passwords, in plain text. Use **SFTP** (over SSH) or HTTPS instead. **SMB** is the Windows file-sharing protocol (network drives, `\\server\share`), also implemented by Samba on Linux and macOS; SMBv1 is obsolete and was exploited by the WannaCry ransomware, so it should be disabled.

## Proxies: forward, reverse and SOCKS5

A **forward proxy** acts for clients: a company routes all browsing through it for filtering and logging; for HTTPS the browser sends `CONNECT host:443` and the proxy just relays the encrypted bytes. A **reverse proxy** acts for servers: nginx, Envoy or a CDN sits in front of your app, terminates TLS, balances load and caches. **SOCKS5** is a lower-level proxy that relays any TCP (and UDP) connection, not just HTTP — SSH's dynamic port forwarding is a SOCKS proxy.

## NTP: keeping clocks honest

Computers' clocks drift by seconds per day. **NTP** asks a time server for the time, measures the round trip, and adjusts gradually. Correct time matters more than it seems: TLS certificates, login tokens, logs and distributed databases all break when clocks disagree.

## IGMP and multicast

Multicast sends one stream to many receivers without the sender duplicating it — IPTV channels and stock-market feeds use it. A TV box joins a channel by sending an **IGMP join**; switches and routers then forward that group's traffic only to ports with members.

## PPPoE: broadband logins

Many DSL and fibre connections authenticate the customer with **PPPoE**: the router discovers the ISP's access concentrator, opens a session, and logs in with the account's username and password before getting a public IP address.

## IPv6 address setup

IPv6 devices can configure themselves: a router periodically sends **Router Advertisements** with the network prefix; the device builds its own address (SLAAC), uses **Neighbor Discovery** instead of ARP, and runs **Duplicate Address Detection** to make sure nobody else has it.

## Modbus and industrial protocols

Factories, power plants and building systems use protocols like **Modbus** (1979): a controller asks a device "read registers 100–109" and gets numbers back. It has **no authentication or encryption** — anyone who can reach the device can command it — so industrial networks must be isolated and closely monitored.

> [!RECAP]
> - **SSH**: verify the host key, authenticate with keys, tunnel anything.
> - **FTP** is plain text — prefer SFTP. **SMB** shares Windows drives; disable SMBv1.
> - **Forward proxies** act for clients, **reverse proxies** for servers, **SOCKS5** relays any connection.
> - **NTP** keeps clocks aligned; **IGMP** joins multicast groups; **PPPoE** logs broadband customers in.
> - **IPv6** self-configures with Router Advertisements and Neighbor Discovery.
> - **Modbus** has no security: isolate industrial networks.
